2. SEAMS
  TGC_File virtuals (+0 read, +4 write, +0x14 is_open, +0x20 open, +0x28 close, +0x30 size) are a
  recording Python model installed right after the original 0x857FE0 ctor returns (0x76120C /
  0x7618CB). Sender and receiver have separate "disks". Open failure is not emulated (it throws
  TGC_FileException 0x869200 because modes carry 0x20000; C++ unwinding). Allocator, CString manager,
  0x401B00, 0x401330, logging 0x404F60 (recorded), the 0x760F20 debug label 0x405D60/0x405A50 are
  seams; CString concatenation 0x4108C0/0x40F4B0 runs original code.

4. FINDINGS
  * ACCEPTED v14 AA.exe REPAIRS THE EXACT-MULTIPLE TAIL. Original: terminal length size % BS, so a
    non-zero multiple of BS sends an empty terminal block and loses the last BS bytes (64 -> 0,
    128 -> 64, 192 -> 128, 49@BS7 -> 42, channel 256 -> 192) while progress reports the full size.
    v14: sender cave 0x9EFF80 uses BS for remainder 0; receiver cave 0x9EFF90 uses min(payload
    length, BS) (unsigned) for remainder 0. Interop: the repair needs both ends (original host ->
    v14 client and v14 host -> original client both still lose 64 of 128 bytes).
    Port: FileTransferConfig.tail = TerminalTail::{Original, V14}; Default = V14 (docs/BASELINE.txt).
  * Size 0: L = 0, no data block; neither side ever closes its file (both images).
  * ".." check: _wcsstr on the name up to its first NUL; ".." anywhere (also "a..b") rejects (log
    0xBF, no open, size still stored, later blocks drained without writes). After an embedded NUL it
    is accepted and the path (length-based concatenation) keeps the NUL; CreateFileW would open the
    truncated name. Destination = profile dir + name, no other validation (absolute names, "\" etc.).
  * Header name length is 16 bits (0x7616CE movzx): 65536+ unit names are cut on the wire while the
    sender opened the full name.
  * Receiver writes a length derived from ITS OWN BlockSize and the header size, not from the
    payload: mismatched BlockSize writes wrong data; a payload shorter than that length is a heap
    over-read in the original (Rust: Error::Protocol). Receiver has no pending-block limit: any
    index >= begin is buffered (window grows to index+1).
  * MaxPendingBlocks limits only the sender read-ahead (end - begin); 0 stalls after the header.
  * Block reads ignore the returned count; buffers are zero-filled (0x767110), so a short read sends
    zeros. Estimate = 32 + 8*len - 3 - (byte0 & 7) (under-counts by 3 + pad, treats file bytes as a
    pad field); for an empty buffer (original exact-multiple tail) the byte read is past the buffer
    (heap-dependent; port uses 0 = what the zero-filled oracle heap shows).
  * Budget: a block is chosen only when its estimate < limit - span - 33; 64-byte blocks estimate
    534..541 bits, so a section carries one only for limit > 587..594 (tight-budget scenario uses
    limits 0x252/0x253 around that edge). v14 also raises the type-5 file
    target 0xC03 -> 0x2403 (0x74E36E) and redirects 0x74BEC8 call 0x74BCB0 -> 0x9EFF40 (send
    scheduling): both are AdminConn code outside file.rs, not ported here.
  * Progress 0x7612D0 = size when begin == L+1 else (begin-2)*BS (wrapping): -128 on a reset
    sender, -64 when only the header is acknowledged.
  * Start does not close a previously open file (restart while sending reopens the handle).

5. CAPS (original value -> port)
  0x7611FA / 0x7618B4  0x74B790(0x100): block-buffer rings, 256 initial slots, grown by 0x74CDB0
                       -> BlockWindow (BTreeMap, sparse, no capacity)
  0x761648             header writer buffer 0x767110(0x100) bytes, grown by 0x767000 -> WireWriter
  0x7610E5             payload buffer of the 32-bit decoded length (hostile length overflows the
                       allocation size) -> Vec after a remaining-bits check
  0x760390             BlockSender windows 0x100 (channel.rs)
  Kept as rules: BlocksPerFrame 20 and BlockSize 64 (wire; both ends must agree), MaxPendingBlocks
  256 (sender-only flow rule, may be raised without breaking peers), 16-bit name length (wire).

6. PROVEN / NOT PROVEN
  Proven (oracle replay): everything in section 3 for both images and both interop directions,
  including BlockSender/BlockReceiver integration at section level.
  Rust-only tests (no oracle): explicit errors (BS 0, block index 2^31-1, backward retire, empty
  slot serialize, over-read, unopened size, hostile payload length, empty header), receiver open
  failure (Catch@0x761BCD: log 0xB9 + UI message, continue; from machine code/pseudocode), StdFile
  round trip through channel sections in a temp directory.
  Not covered: real sockets/datagrams, type-5 packet writer/reader (0x74E280/0x75A350 incl. the
  "not most recent" drop), UpdateFileTransferStatus 0x74F310, the sender-side open exception path
  (where it is caught upstream is unknown), OS share modes. No end-to-end network claim.
