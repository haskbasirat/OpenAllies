# Development-10 packaging readiness draft

No Development-10 release has been created or built by this audit. No client, original asset, save, profile, or prior release was changed. The only executable inspected was the existing Dev09 PE file; it was not launched. Eleven synthetic packaging tests pass in generated temporary directories inside this research folder, including the separately labeled diagnostic mode. This preparation is separate from the native battle work.

The draft helper is `package.py`. Root owns final build, documents and package invocation. `stage` always refuses if the real `release/Development-10` already exists. All files are created exclusively, without overwriting; a failed partial stage is retained for inspection and is never automatically deleted. `seal` only accepts this helper's own exact staged inventory and matching source/build fingerprints. It requires separately supplied native-battle, controls, visual, copied-package CLI, and independent acceptance evidence. A successful map-load diagnostic cannot seal as a playable battle. `verify` checks inventory hashes, ZIP bytes/CRC and previous-release preservation; it does not certify gameplay.

The user also requested Development-10 to test current progress when battle remains unfinished. A separate **diagnostic** mode now permits that truthful release. It keeps `playable_battle: false` and `battle_status: "unavailable"`, requires disabled unimplemented battle UI and actual architecture/dependency/assets/copied CLI/render/independent acceptance, and writes `AxisAlliesRust-Development-10-DIAGNOSTIC.zip`. The strict playable seal is unchanged. Diagnostic mode never infers native initialization, controls, clock/tick or combat success. Its exact command/validation contract appears below.

`payload-plan-draft.json` is a read-only initial inventory. It verifies and records **3,754 existing files across Development-08 and Development-09**, including their ZIPs. It proposes **1,869 cache files / 91,888,045 bytes**. Current `assets-cache` has 2,000 files; Dev09 packaged 1,811. The proposal retains the material sidecar, 46 top-level preview rigs, the ordinary animation manifest, `game-rigs.json` and all 58 named game rigs, plus the two menu movie indexes and their 1,760 JPEG frames. It excludes `.reference.json`, research export logs, phase3-staging copies and unused promotion metadata. Relative to Dev09 it adds 59 named gameplay cache files and omits the unused `animation/promoted-families.json`. The game rig manifest itself still records skipped model/clip entries; inclusion is not a claim that every model or animation is supported. Recompute the closure after the battle's actual graphics/animation bindings are frozen.

At the initial audit, the source was a Dev09 client: its title named Development 09, Single Player/Multiplayer were disabled, `--map-restore-check` reported `battle_ready=false`, and the live scene constructed render/picking bindings from original placement records. The renderer could apply supplied snapshots and isolated infantry animation; that was not an initialized, ticking native battle. These are dated source-audit findings. Root is updating the Dev10 client and must verify its actual final title/help/disabled battle status and available diagnostics before packaging.

The existing Dev09 EXE is AMD64 PE32+, large-address-aware, with `PerMonitorV2` and `asInvoker` manifest markers. `dev09-pe-audit.json` pins its exact hash and static import list. It imports `VCRUNTIME140.dll` and Windows CRT API-set DLLs, so an extracted folder needs the matching x64 MSVC/UCRT runtime available on the receiving machine. The package has no bundled runtime DLLs. Vulkan/DX12 graphics backends also need suitable installed OS/driver support; PE static imports do not enumerate every DLL dynamically loaded by graphics/audio. Do the same inspection on the final Dev10 candidate rather than inheriting this Dev09 dependency claim.

The package is not standalone. It currently needs the original `Data.rwd` and the existing reconstruction tree: `game` map data; original Data rules/UI/fonts/localization/NIF/KF resources; converted models/textures/terrain; matching `native-game/runtime-expanded-v14` source overlays; and recovered Skins/Music/Speech. Caches accompany the executable; copying caches does not copy that whole external tree. Asset discovery searches working-directory and executable ancestors for `game/data/maps/index.json`; the reliable portable invocation is `AxisAlliesRust.exe --assets <reconstruction-directory>`. Moving only the ZIP to a machine without these resources is insufficient. No original EXE bridge or gameplay fallback is included or proposed.
