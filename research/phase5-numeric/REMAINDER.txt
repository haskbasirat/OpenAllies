EXACT FINITE REMAINDER AND EMULATOR DISCREPANCY

Binary::remainder_trunc implements a quotient truncated toward zero, preserving
the dividend sign including negative zero. It aligns exact dyadic magnitudes,
uses integer modulo, then checks the existing supported extended exponent range.
There is no host floating-point calculation or precision-control rounding in
the production implementation. A zero divisor is an explicit error.

The first synthetic Unicorn FPREM oracle was checked against actual host x87.
It was wrong for 1,188 of 3,696 tested cases, primarily extreme exponent ratios.
For example binary32 0.1 modulo three minimum subnormals is one minimum
subnormal, confirmed by integer modulus and hardware; the emulator returned0.
The original fixture is retained unchanged as remainder-vectors.json. The
discrepancy inventory records both values; the implementation was not weakened
to match the emulator.

The acceptance fixture is remainder-hardware-vectors.json, generated by the
standalone test-only host_remainder.rs through capture_host_remainder.py.
Input/output bytes, generator/source/executable hashes and raw emulator results
are recorded. Rust tests compare the entire extended value before storage and
repeat all hardware instructions, across three control-word modes. Signed-zero,
zero-divisor and final binary32 overflow behavior have separate checks.

All 3,696 hardware-backed cases pass. Earlier square-root and arithmetic suites
still pass. Native game control-flow fixtures are separate and retain their
scopes. An emulated original instruction sequence is not universal hardware
proof, particularly outside the physically meaningful map-coordinate domain.
Full map construction and the actual simulation FPU lifecycle remain unfinished.
